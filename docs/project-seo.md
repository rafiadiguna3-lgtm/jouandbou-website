# Public project pages and share previews

The 8 documented Jou projects and 7 Bou concepts in `site/project-catalog.mjs` have public `/projects/.../` URLs. Models with no finished project story and under-construction projects keep their existing hash routes and are excluded from the sitemap/public directory.

`npm run build` verifies source/asset hashes, copies the site, and generates a static HTML file for each published project plus `/projects/`. Each project contains its own title, description, canonical URL, Open Graph/Twitter JPEG metadata, WebPage/CreativeWork and breadcrumb data, and real text and photographs visible without JavaScript. Project pages permit large search-image previews. Homepage SEO and its separate tab/share favicon behavior remain.

The static content is also a readable loading/failure fallback. Once the app opens the selected detail UI, it removes the fallback. `project-routing.mjs` normalizes old hash links, handles public paths, updates in-app metadata and restores homepage metadata. A root base URL keeps relative assets valid after history changes. `about.mjs`, `app.mjs`, `bou.mjs` and `phone-intro.mjs` read the shared route adapter. Project/back links keep SPA behavior; a modified click can open the real page in a new tab.

To update project content: edit the existing project stories or Bou data, adjust the reviewed project list/descriptions in `scripts/build-project-catalog.mjs`, then run `npm run build:project-catalog`. To regenerate the 1200×630 JPEG previews from existing photographs/illustrations, run `npm run build:project-previews` with Chromium available. No photographic redraw is used. Add new assets to the manifest, document intentional edits, then `npm run manifest:update` and build. Deployment builds require Node only; committed catalog/previews are used without launching Chromium.

`npm run dev` now builds and serves dist on port 5173 so nested pages work locally; rebuild/restart after changing source (there is no hot reload). Run `npm run test:projects` for generated-page integrity and browser SEO tests; run the complete browser suite after routing changes.

After Cloudflare deployment, verify a project URL returns HTTP 200 with its project metadata directly in the response; its JPEG returns image/jpeg; the sitemap lists the published paths; an unknown path returns a real 404; and www redirects to the apex while preserving project paths. Both custom domains must reach the same deployment. Submit the sitemap and request project indexing through Search Console when production is confirmed. Indexing, rankings, rich results and WhatsApp cache refresh are controlled externally and cannot be guaranteed. Existing sent previews may remain cached. Native Safari/device behavior and live production routing cannot be verified from this cloud environment while its proxy blocks the domains.

Validation for this implementation: build succeeded; 66 browser tests and 15 asset/queue/resolution/generated-page tests passed. All 15 project metadata responses and readable static bodies were checked with JavaScript disabled; SPA navigation, old hash links, nested-page reload, Back/Forward, Bou return links and all prior map/gallery/phone regressions passed. Development serving of nested project URLs was exercised, with visual checks of static desktop content and the existing phone detail UI. Tests use Linux Chromium emulation, not native Safari or the actual Google/WhatsApp crawlers.
